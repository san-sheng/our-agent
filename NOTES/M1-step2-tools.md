## 0. 一句话总结

工具系统 = Agent 的「手脚」。核心是一个**注册表**：
模型看到工具描述（schema）→ 决定调用哪个 → 框架按名字找到函数 → 执行 → 结果回填。

```
模型看到的工具定义 (schemas)         框架手里的真实函数
┌─────────────────────────────┐     ┌──────────────────────┐
│ name + description + params │     │ Tool 子类的 run()    │
│ (发给模型，让它选)            │ ←→  │ (Python 代码，执行)   │
└─────────────────────────────┘     └──────────────────────┘
```

对应核心公式：**工具 = Action Space（动作空间）**——Agent 能做的所有事情。

---

## 1. 工具的三要素（Tool 抽象 = 4 个类属性 + 1 个方法）

```python
class Tool:
    name: str = ""          # 模型看到的工具名（全局唯一）
    description: str = ""   # 什么时候用 + 边界条件（反例）
    parameters: dict = {}   # JSON Schema：参数类型/约束/示例
    def run(self, **kwargs) -> str: ...  # 实际执行
```

**为什么是「描述」而不是「实现」占据类的大半？**
因为模型的决策只依赖描述——它永远看不到 run() 的代码。
工具设计的好坏 = 描述能否让模型在正确时机做出正确选择。

`schema()` 方法把三要素包装成 OpenAI function calling 格式：
```python
{"type": "function", "function": {"name": ..., "description": ..., "parameters": ...}}
```
这个格式是模型 API 的通用语言，`llm/client.py` 直接把它作为 tools 参数发出去。

---

## 2. 描述的艺术（书 Ch4 重点，也是这次最大的认知）

### 2.1 写「什么时候用」，不写「能做什么」

| 写法 | 效果 |
|------|------|
| ❌ "读取文件" | 只说了功能，模型不知道该在什么时候选它 |
| ✅ "当需要查看代码、配置、日志或文档时使用" | 给了调用决策的触发条件 |

### 2.2 边界条件（反例）比能力本身更重要

书里原话：**大多数工具调用失败的根因，不是模型不知道工具能做什么，
而是不知道工具不能做什么。**

所以我们在每个工具描述里都写了「做不到什么」：
- read_file：「不能读取图片等二进制文件」
- write_file：「会覆盖全部现有内容，不是追加也不是局部修改」
- run_command：「禁止 rm/mkfs/shutdown/curl 等危险操作；输出超 8000 字符会被截断」

### 2.3 参数描述带具体示例

`path: "文件路径（绝对路径或相对路径），例如 /home/user/project/main.py"`

书里说：模型专注复杂任务时，确认参数格式只占注意力一小部分，
具体例子让它直接套用，无需额外思考。

### 2.4 调试原则（书 Ch4 原文）

> 当 Agent 频繁选错工具时，应**优先检查工具描述**而不是怀疑模型能力。
> 修正工具描述的投入产出比，远高于更换一个更强的模型。

---

## 3. 参数保真性（最隐蔽的坑，书 Ch4 两个反例）

### 反例一：静默输入转换（Cursor 弯引号事件）

工具把中文弯引号（`“”`）静默转成英文直引号（`""`）→
模型读文件看到弯引号 → 原样传入 old_string → 工具内部已转换 → 「未找到匹配」→
模型反复失败却无法理解为什么「明明看到的内容工具找不到」。

### 反例二：静默参数注入（IDE 的 git commit）

工具自动给所有 `git commit` 追加额外参数 → 旧版 git 不支持 → 报错。
模型不断调整提交信息措辞，但无论怎么改都失败。

### 教训（书 Ch4 原文）

> **模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差。**
> 工具的参数传递必须保持透明，不得在模型不知情的情况下修改输入或输出。

我们怎么落实：run() 原样接收 kwargs 直接执行，不做「智能修正」；
write_file 会自动建父目录——这是**显式行为**，写进了描述和注释，
不是偷偷帮模型做事。

## 4. 为什么 schema 手写，不自动生成？

真实框架（如 instructor、Pydantic）会从 Python 类型注解自动推断 JSON Schema——
省事但引入魔法（inspect.signature + 类型映射表）。

**我们 M1 刻意手写**：学习阶段先看清「工具定义长什么样」，
每一步都看得见摸得着。自动生成是 M4 再考虑的优化方向。

这也呼应书里的「能力表达形式的选择」：
- 参数复杂、稳定 → 专用工具（结构化 schema 引导弱模型正确传参）
- 参数简单、频繁变 → Skill + 通用执行器（M2+ 再说）

## 5. Registry：名字 → 函数 的映射表（核心设计）

### 5.1 三个职责

```python
class ToolRegistry:
    def register(self, tool: Tool) -> None   # 收编工具（重名报错）
    def schemas(self) -> list[dict]           # 生成模型看到的全部工具定义
    def execute(self, name, arguments) -> str # 模型决定调用后，按名执行
```

### 5.2 核心认知：工具层错误是「模型的输入」，不是「系统故障」

这是这次最重要的设计决策。execute() 里**任何错误都不抛异常**，
而是返回 JSON 错误字符串回填给模型：

| 场景 | 处理 |
|------|------|
| 模型幻觉编造不存在的工具名 | 返回 `{"error": "未知工具: xxx"}` |
| 参数畸形（缺 required 参数） | 捕获 TypeError → 返回 `{"error": "参数错误: ..."}` |
| 工具内部抛异常 | 捕获 Exception → 返回 `{"error": "工具执行失败: ..."}` |

**为什么？** 因为 ReAct 循环里，工具结果会作为 tool 消息回填给模型。
模型需要看到「我错了/失败了」才能自我纠正。如果抛异常打断循环，
Agent 就死了。错误回填 = 让循环继续 = 让模型有机会改。

类比 C++：这不是异常（throw），是**返回值携带错误码**（返回 Optional/Result）——
调用方（模型）自己决定怎么处理。

### 5.3 为什么重名直接报错

模型通过名字区分工具。两个工具同名 → 模型无法分辨 → 可能调用到错误的那个。
所以 register 时查重，重名抛 ValueError（这是**编程错误**，不是运行时错误，
应该立刻暴露）。

## 6. 三个内置工具的设计取舍

### 6.1 read_file（感知工具）—— 书 Ch4 感知工具原则

- **offset/limit 按需读取**：大文件分段读，不一次塞满上下文
- **截断显式可见**：返回 `(第 X-Y 行 / 共 N 行)`——即使没截断也告诉总行数。
  书里原文：**静默截断是危险的——模型会误以为自己看到了全部内容，
  基于不完整的信息做错误判断**
- **返回带行号**：`1|内容` 格式——M4 的编辑工具需要精确定位
- 只读性红利（书 Ch4）：感知工具不改世界 → 结果可缓存、调用可并行（M2+ 用）

### 6.2 write_file（执行工具）

- **覆盖语义明确**：创建或完全重写，不追加、不局部修改——描述里写清楚
- **自动建父目录**：显式行为，写在注释里（模型写嵌套路径不用先 mkdir）
- 安全边界（书 Ch4：执行工具错误代价可能极高）M1 刻意最小化——
  「是否在项目目录内/沙盒」是 M4 的事，M1 先跑通闭环

### 6.3 run_command（执行工具）—— 安全四件套

1. **危险命令黑名单**（第一层：输入验证）
   - `rm / dd / mkfs / shutdown / chmod / chown / curl / wget / kill ...`
   - 快速失败：发现即拒绝，不执行、不尝试修正
   - **书 Ch4 原文警告：黑名单只是最基础的防护层，不应作为唯一手段**
     ——攻击者可用变形命令绕过（M4 上语义解析 + 沙盒）
2. **timeout 熔断**：30s 超时杀掉——防止交互式命令挂死 ReAct 循环
3. **输出截断**：8000 字符上限，截断时显式注明（静默截断危险的延伸）
4. **JSON 输出**：exit_code + stdout + stderr + truncated

### 6.4 踩坑记录：shlex.quote 不是 JSON 转义！

初版用 `shlex.quote(stdout)` 拼 JSON 字符串——shlex.quote 是给 **shell**
用的，只保证「shell 能解析」，不保证「JSON 合法」。输出含换行时直接制造
非法 JSON（JSONDecodeError）。

**修复**：stdout/stderr 是任意文本（可能含换行/引号/非 ASCII），
必须用 `json.dumps` 序列化，绝不能手工拼 JSON。

教训（C++ 视角类比）：shlex.quote ≈ 只做了 shell 层的转义，
忘记 JSON 层还需要一层转义——跨层传递时每层都要自己的编码。

## 7. 对照：书配套代码的做法 vs 我们的做法

书配套 chapter1/context/agent.py 里，工具描述是**硬编码的 dict 列表**：

```python
self._get_tools_description() -> List[Dict[str, Any]]:
    return [{
        "type": "function",
        "function": {
            "name": "parse_pdf",
            "description": "...",
            "parameters": {...}   # 手写，和函数实现分离
        }
    }, ...]
```

问题：描述和实现**分离**——改函数签名时容易忘了改描述，两边漂移。

我们的做法：描述 + 实现**绑定在同一个类里**（Tool 子类），
改一个地方，schema 自动跟着变。这就是「结构化工具抽象」的意义。
