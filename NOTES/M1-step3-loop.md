## 0. 一句话总结

`loop.py` 是「胶水层」：把 LLM（大脑）+ 工具（手脚）串成
**思考 → 调工具 → 执行 → 回填 → 再思考** 的循环，直到模型不再调工具、输出最终回答。

核心公式（书 Ch1）：**Agent = LLM + 上下文 + 工具**
三件套在代码里的落点：LLM=`llm/client.py`（第 1 步），工具=`tools/`（第 2 步），
**上下文的管理者 + 循环驱动器 = `agent/loop.py`（本步）**。

## 1. ReAct 循环：为什么是循环（书 Ch1 核心）

### 轨迹的累积性

模型下一轮**必须看到自己上一轮想了什么、调了什么、得到了什么**，
才能理解「当前处于任务的哪个阶段」：

```
第 1 轮：模型想 → 决定调 read_file
第 2 轮：模型看到读取结果 → 再想 → 决定调 run_command
第 3 轮：模型看到命令结果 → 信息足够 → 直接回答
```

这就是 ReAct 是「循环」而不是「一问一答」的根本原因——
工具结果必须回填给模型，循环才有意义。

类比 C++：这不是 `for` / `while` 语法上的循环，是**状态机 + 终止条件**——
循环体 = 一轮「思考 + 执行」，终止条件 = 模型不再调工具。

## 2. 轨迹 = run() 局部变量

每次 `run()` 全新构造：`system + user` 开头，逐步累积 assistant / tool 消息。

- 一次任务一条轨迹，语义清晰
- **跨任务记忆是 M3 的事，M1 刻意不做**
- 类比 C++：轨迹 ≈ 函数内的局部 `std::vector`，每次调用重新构造。

## 3. 关键设计点（每个都是取舍）

### 3.1 assistant 消息原样回填（含 tool_calls）

模型必须看到自己刚才发起的工具调用（`tool_calls` 原样回填），
否则不知道自己在循环的哪一步。回填的是**纯 dict** 不是 SDK 对象——
发给模型的 messages 保持标准 JSON 结构，SDK 序列化不炸。

### 3.2 tool 消息为什么带 tool_call_id，不带 name

```python
messages.append({"role": "tool", "tool_call_id": tc["id"], "content": result})
```

两层原因：

1. **协议硬性要求**：tool 消息必须对应 assistant 那条 tool_calls 里的 id，
   带不上/对不上 API 直接报错。
2. **本质：name 不唯一，id 唯一**。模型一轮可以发起**多个**工具调用，
   甚至同一工具调两次（读两个文件）——name 无法区分两条结果分别是谁的。
   而每个调用有唯一 id，`tool_call_id` 就是「结果 ↔ 调用」的对照表。

**id 由模型生成，框架只做无脑透传**：不生成、不校验、不改写，
只保证「谁发起的调用，结果就还给谁」。

### 3.3 坏 JSON 参数 → 回填错误，不抛异常

参数来自模型 = 不可信输入。`json.loads` 失败不抛异常，
而是用 `json.dumps` 包成错误串作为 tool 消息回填——让模型看到错误自己改正。

延续 registry「**错误是模型的输入**」原则（第 2 步笔记 §5.2）：
错误不打断循环 = 给模型修正的机会。类比 C++：返回值携带错误码，不是 throw。

### 3.4 max_iterations 熔断（书 Ch1 护栏·控制流层错误恢复）

模型可能死循环：反复调同一个失败工具、反复思考不回答。
达到上限就停止，返回「任务未完成 + 模型最后输出」，不让 token 白烧。

### 3.5 循环内 LLM 异常不吞，向上抛

重试已由 `llm/client.py` 处理（API 层：指数退避 + 抖动，第 1 步笔记 §4）。
重试耗尽 = 无法恢复的错误，loop 层不假装能处理，抛给 CLI 层显示。

### 3.6 verbose：只影响日志，不影响逻辑

- 构造入参，默认 `True`。两处打印：每轮调了哪些工具、循环完成。
- 核心行为（轨迹回填 / 执行工具 / 熔断）完全不依赖它。
- 测试注入 `verbose=False` 防刷屏（tests/test_loop.py:50）。
- 类比 C++：≈ debug 开关 / NDEBUG——工程便利，不是功能。

## 4. 系统提示词（SYSTEM_PROMPT）

三句话定行为，覆盖循环的成败关键：

1. **什么时候调工具**：需要读文件/执行命令等操作时调用对应工具
2. **看到错误怎么办**：错误是反馈，调整策略，不要重复同样的失败调用
3. **什么时候停**：任务完成或信息足够时直接输出最终答案，别再调工具

静态前缀，每轮都原样发送（KV Cache 友好）。

---

## 5. CLI 入口（cli.py）

两种模式：
- **REPL**：`python cli.py`，每行输入一个任务
- **单次模式**：`python cli.py "任务"`，执行一次退出（脚本调用 / demo 验收用）

为什么是 REPL 而不是「一个任务跑完就退出」：**每行输入 = 新任务 = 新轨迹**，
多轮对话历史是 M2 上下文工程的事，M1 刻意不做。

fail-fast：配置缺失让 `LLMClient()` 构造直接抛 `ValueError`，
启动即暴露，不带病运行（第 1 步笔记 §6.2）。

## 6. 测试策略：假 LLM 驱动（Harness 工程思想）

**不真调 API**。`_FakeClient` 预置响应序列，按顺序弹出，并记录每次收到的 messages。

为什么能这样测：Agent 只依赖 `client.chat(messages, tools)` 的**返回格式**
（`{"role", "content", "tool_calls"}`），不关心背后是不是真模型——
把「模型行为」参数化，测的是框架本身。

这是 Harness 工程的核心思想：**模型之外的部分可以且应该被确定性测试。**

4 个用例覆盖循环的全部行为：

| 用例 | 验证点 |
|------|--------|
| 直接回答 | 只调一次 LLM，直接返回 content |
| 工具循环后回答 | 轨迹累积：第二轮 roles = system/user/assistant/tool；tool 消息带 tool_call_id |
| 坏 JSON 自纠 | 错误回填为 tool 消息内容，循环不崩 |
| 熔断 | 只调 max_iterations 次 LLM，没多烧 token |
