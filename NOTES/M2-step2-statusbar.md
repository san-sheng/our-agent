## 0. 一句话总结

M2 第 2 步做两件事：

1. **状态栏**：每轮请求**末尾**注入一条 user-role meta 消息——时间戳 / 工具计数 /
   进度（本轮第几轮）/ TODO。模型每次生成前「瞥一眼」就知道自己干到哪了，
   不用再从几千个 token 的原始轨迹里现算。
2. **熔断摘要**（落实 2026-08-24 拍板）：任务熔断时不再「什么都不留」，
   生成一条复用状态栏格式的 `[UNFINISHED]` 摘要
   （任务目标 / 已完成 / 下一步 / 失败点）写入 history，
   让下一轮能「接着办完」，又不被原始垃圾轨迹误导。

书里的核心概念：**上下文窗口是一台只有一半的检索引擎**——
模型擅长检索、不擅长归纳；状态栏就是补上的「提炼层」。

## 1. 为什么需要状态栏：「只有一半的检索引擎」

书 Ch2 §2.6 的理论基础（注意力机制的本质特性）：

> **上下文学习更像检索而非推理**——模型擅长从已有内容中查找信息，
> 但不擅长主动归纳和总结。

「检索」这一半非常强：你问什么，注意力就能从成千上万个 token 里捞相关记录。
但它缺了「提炼层」：上下文里的东西**从来不会被自动数一遍、建个索引、
就地质总结成一条结论**——「一共调了几次工具」「进展到哪一步」，
模型每次要用都得从原始记录里**现算一遍**，代价随内容量 N 上涨。

实验 2-7（注意力可视化）+ 上下文蒸馏基准（2.4 万次评测、11 个模型）：

| 模型强弱 | 状态栏带来的变化 |
|---------|----------------|
| 弱模型（2B 级） | **补回来的是准确率**——最弱的涨 40~54 个百分点，本地 2B 直接追平不带状态栏的前沿大模型 |
| 强模型 | **省下来的是效率**——思考量、延迟、花费各降约一个数量级 |
| 最本质 | 不带状态栏时每次查询的思考量随上下文变长**持续增长**；带上后**基本恒定**——注意力牢牢锁在状态栏那几格上 |

## 2. 状态栏长什么样

- **位置**：上下文末尾的 user-role meta 消息（不属于用户消息、模型输出或工具结果）
- **形态**：**键值对**，不是散文。论文里把同样的状态写成散文，效果明显更差——
  模型还得把散文读一遍、解析出来，等于又回到了「扫描」
- **性质**：系统提示词是「入职时发的员工手册，定下来就不变」；
  状态栏是「贴在屏幕边缘的实时仪表盘，随任务推进不断更新」

我们定的三格（M2 第 2 步规划）：

```text
【状态栏】
时间: 2026-08-25 02:40:30
工具: 已调用 0 次（无）
进度: 第 1/10 轮
TODO: 输出最终回答
```

## 3. 三条实践铁律 + 一个风险

**一、状态栏要用代码维护，别拿大模型去维护。**
一个 20 行的正则函数就能达到「标准答案」级别；让前沿大模型**一次性**读完整段
历史、吐出统计结果，反而在大多数格子上出错，把下游准确率拖得比不用还低。
（要让 LLM 抽，也要逐条抽取、再由代码汇总，绝不让它批量统计。）
→ 我们的工具计数就是循环里 `tool_counts[name] += 1`，纯代码。

**二、想删掉原始上下文之前，先确认状态栏覆盖了所有会被问到的问题。**
状态栏是**有损投影**——只提前算了「预想会被问到」的维度。问到一个没算过的维度，
带着状态栏删原文，准确率会断崖式崩塌（论文极端测试：Claude 从 100% 掉到 7.6%）。
→ 我们 M2 阶段**不删原文**，状态栏和原始轨迹共存的阶段，这条暂不涉及。

**三、把状态栏的准确率当成一线生产指标来盯。**
**模型几乎无条件地相信状态栏**——你写「打了 3 次」，它就当真是 3 次，
不核对、不重算。写错 = 错误原样传进最终答案。容错空间：数错 10% 以内收益还能
保住大半，越过这条线，带着错状态栏比不带还糟。
→ 我们的工具计数是从循环里的事实数据算的，不是模型猜的；测试锁定格式和数值。

**风险：状态栏投毒。** 状态栏信息被模型高度信任（这正是它有效的原因），
一旦内容来自可被外部污染的数据源（比如直接把网页片段写进状态栏），
这台「仪器」读出的就是错的刻度。→ 我们只放时间/工具计数/进度这类框架自有的
可信观测，绝不把外部内容塞进去。

## 4. 我们的实现（agent/loop.py）

### 4.1 注入方式：请求副本，不进核心轨迹

```python
req = list(messages) + [
    {"role": "user", "content": self._status_bar(iteration + 1, tool_counts)}
]
resp = self._client.chat(req, tools=schemas)
```

关键取舍：**状态栏只拼进发送给模型的请求（req），不进核心轨迹 messages**。

- 会话历史 (`self._history`) 不被过期状态栏污染——否则上一轮的旧时间、
  旧计数会留在多轮记忆里误导后面的任务
- 守住「历史只追加不改写」（KV Cache 前缀稳定）的不变式
- 每轮重新生成、即时反映进展：第 1 轮「已调用 0 次」，第 2 轮「已调用 1 次（run_command×1）」

### 4.2 时间来源可注入（测试可复现）

```python
clock: Callable[[], datetime] = datetime.now
```

默认真实时钟；测试注入固定时间，让「时间戳」断言可复现（状态栏必须可验证——
书铁律三）。

### 4.3 熔断 [UNFINISHED] 摘要（2026-08-24 拍板落实）

熔断路径从「什么都不留」改成：

```python
summary = self._unfinished_summary(task, tool_counts)
failed_user = dict(messages[user_start])
failed_user["content"] = f"{failed_user['content']}\n\n{summary}"
self._history.append(failed_user)
```

- **复用状态栏格式**（键值对 + 同一标题族的 `【状态栏 · UNFINISHED】`）
- **四个字段**：任务目标 / 已完成步骤 / 下一步 / 失败点
- **附加到任务那条 user 消息**一起存：history 只多一条消息，
  模型下次追问「刚才那个任务帮我办完」时能看到旧任务 + 失败原因，
  但不会看到一堆重复失败的原始轨迹
- 任务目标截断到 100 字符（摘要要紧凑，低 token 成本）

为什么不是「完全不保存」也不是「存原始轨迹」：
完全不保存 → 「接着办完」无从下手；存原始轨迹 → 半截子轨迹看着像做完了，
反而误导（M2 第 1 步笔记 §2.1 讨论过的取舍）。

## 5. 测试策略（39 绿）

### 5.1 状态栏是 meta 消息：断言轨迹前先滤掉

新增 `_strip_status()`：滤掉 role=user 且内容以 `【状态栏】` 开头的消息。
已有轨迹断言（roles 序列、tool_msg 位置）都先滤一遍——
状态栏是框架的「仪表盘」，不属于对话主体，断言轨迹结构时不该算它。

注意：`【状态栏 · UNFINISHED】` 不以 `【状态栏】` 开头（栏后面是空格），
所以失败摘要在断言里不会被滤掉——正是我们要查的。

## 6. 验证结果（真实 API 冒烟）

```text
=== R1：多步任务，但只给 2 轮迭代（逼熔断）===
[Agent] 第 1 轮调用工具: read_file
[Agent] 第 2 轮调用工具: write_file
R1 返回: 任务未完成：已达到最大迭代次数 2。……

熔断后 history：
  [user] 读 DESIGN.md，统计有多少行，把结果写到 /tmp/our-agent-stats.txt

【状态栏 · UNFINISHED】
时间: 2026-08-25 02:40:30
任务目标: 读 DESIGN.md，统计有多少行，把结果写到 /tmp/our-agent-stats.txt
已完成: 工具调用 2 次（read_file×1、write_file×1）
下一步: 输出最终回答（未完成）
失败点: 达到最大迭代次数 2（熔断）

=== R2：同一会话追问，给足迭代次数（6）===
[Agent] 第 1 轮调用工具: run_command, read_file
[Agent] 第 2 轮调用工具: write_file
[Agent] 第 3 轮调用工具: run_command
[Agent] 完成（第 4 轮）
R2 返回: 任务已办完 ✅  上次任务在达到最大迭代次数（熔断）时只完成了
read_file 和 write_file 两步，还没来得及输出最终回答，所以状态栏显示「未完成」。
……统计行数：wc -l DESIGN.md 共 230 行；已写入 /tmp/our-agent-stats.txt。
```

三件事被验证：

1. **熔断摘要写入 history**：R1 熔断后 history 只有一条任务消息 + 摘要，格式/字段齐全
2. **模型真的读了状态栏**：R2 的回答直接引用「状态栏显示『未完成』」——提炼层生效，
   模型不再需要从半截子轨迹里猜自己干到哪了
3. **「接着办完」链路打通**：追问后模型补齐 read → wc → write → 验证，`wc -l`
   与文件写入的 230 一致（可复现）；且 **没有原始垃圾轨迹污染**——R1 那轮
   read_file/write_file 的具体结果没留在 history 里，模型是靠摘要 + 自己的新调用补完的

缓存观察：状态栏追加在上下文**末尾**，前缀（system + history + 任务 + 轨迹）稳定，
命中率在稳定轮次回到 97%（第 4 轮 hit=4864/miss=163）——追加尾部不破坏 KV Cache 前缀。
